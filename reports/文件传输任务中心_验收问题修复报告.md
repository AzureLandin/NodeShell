## 3. P1 问题一：任务状态事件乱序

### 3.1 问题位置

- [internal/sftpservice/transfer_manager.go:238](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:238)
- [internal/sftpservice/transfer_manager.go:241](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:241)
- [internal/sftpservice/transfer_manager.go:462](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:462)
- [src/renderer/src/hooks/useTransferTasks.ts:73](E:/Projects/NodeShell/src/renderer/src/hooks/useTransferTasks.ts:73)

### 3.2 根因

`EnqueueUpload` 和 `EnqueueDownload` 的执行顺序是：

```go
m.scheduleLocked() // 这里启动 goroutine，任务状态已改为 running
m.mu.Unlock()

m.sink.Emit(EventTransferTask, queuedDTO) // 之后才发送 queued
```

`scheduleLocked()` 会启动 goroutine，goroutine 内部立即发送运行态事件。由于 queued 事件是在解锁后单独发送，实际接收顺序可能为：

```text
running -> succeeded -> queued
```

前端 Hook 在收到事件后按 `taskId` 直接 `next.set(task.taskId, task)`，没有事件版本、状态等级或时间校验，因此较旧的 queued 事件会覆盖较新的终态。

### 3.3 用户影响

- 快速完成的小文件尤其容易触发；
- 任务可能最终显示为“排队中”；
- `finishedAt` 被 queued 事件覆盖为空；
- 成功任务不会按 8 秒自动消失；
- 活跃任务数量可能长期多 1；
- 重试任务也可能出现相同问题。

### 3.4 修复要求

采用“状态快照先发，调度后启动”的顺序，保证任何任务的首次事件一定是 queued：

```text
创建任务
记录 queued 快照
发送 queued 快照
启动可运行任务
发送 running 快照
```

推荐实现方式：

1. 在 `EnqueueUpload`/`EnqueueDownload` 加锁期间创建任务并加入队列；
2. 收集 queued DTO；
3. 解锁；
4. 先按创建顺序发送 queued DTO；
5. 再调用只负责启动任务的调度方法；
6. 调度方法启动 goroutine 前发送或安排 running DTO，确保事件顺序可控。

如果为了锁粒度不希望在解锁后调用调度，也可以让 `scheduleLocked` 返回待启动任务和 running DTO，由调用者严格按照 `queued -> running` 顺序发送，再启动执行协程。禁止在尚未发出 queued 事件前启动会发送 running 的 goroutine。

### 3.5 前端防御性修复

后端顺序修复是必需项，前端还应增加事件防回退逻辑：

- 已有终态 `succeeded/failed/cancelled` 后，忽略 queued/running/finalizing 旧事件；
- 已有 `transferred` 较大值时，忽略更小的进度事件；
- 对同一 taskId 的事件保存 `startedAt/finishedAt/state`，使用状态转换规则过滤非法回退；
- 终态不可被非终态覆盖，除非明确收到新的 retry taskId。

不能只依赖前端过滤，因为后端事件顺序仍会影响其他消费者和任务快照。

### 3.6 必须新增测试

后端：

1. 使用一个立即返回的 runner，记录同一 taskId 的事件顺序；
2. 断言顺序至少为 `queued -> running -> succeeded`；
3. 同时覆盖立即失败和立即取消；
4. 覆盖 upload、download 和 retry；
5. 断言 queued 不会出现在任何终态之后。

前端：

1. 先发送 succeeded，再发送 queued，任务仍为 succeeded；
2. 先发送 transferred=500，再发送 transferred=100，任务进度不回退；
3. 终态任务仍具有 `finishedAt` 并能自动清理。

## 4. P1 问题二：排队下载的远端路径没有固定

### 4.1 问题位置

- [src/renderer/src/components/SftpPanel.tsx:262-269](E:/Projects/NodeShell/src/renderer/src/components/SftpPanel.tsx:262)
- [internal/sftpservice/transfer_manager.go:249-288](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:249)
- [internal/sftpservice/sftpservice.go:1129](E:/Projects/NodeShell/internal/sftpservice/sftpservice.go:1129)

### 4.2 根因

SFTP 面板下载时传入的是当前列表项名称：

```ts
window.api.transfer.chooseDownloadTarget(sessionId, entry.name, entry.name)
```

任务管理器只保存相对 `remotePath`：

```go
remotePath: remotePath,
```

任务真正开始时，`DownloadWithContext` 使用执行时 session 的当前目录：

```go
remote := JoinRemote(cwd, remotePath)
```

所以用户在 `/dir-a` 点击下载、任务排队后切换到 `/dir-b`，任务可能实际读取 `/dir-b/file.txt`。

### 4.3 修复要求

任务创建时必须保存已经解析过的、不可随当前 UI 变化的远端绝对路径。

推荐方案：

1. SFTP 面板使用 `entry.path` 或 `JoinRemote(cwd, entry.name)` 传入完整远端路径；
2. `TransferEnqueueDownload` 接收到远端路径后，在创建任务时调用 session 的当前 cwd 解析相对路径；
3. 将解析后的绝对路径保存到 task 的 `remotePath`；
4. `DownloadWithContext` 只接收并使用这个绝对路径，不再次读取 session 当前 cwd。

建议明确区分：

```go
type Task struct {
    remotePath string // 创建任务时解析后的绝对远端文件路径
}
```

如果使用 `entry.path`，必须确认列表 API 返回的 `path` 是绝对远端路径，而不是仅用于 UI key 的相对路径。不能只改变量名而不验证语义。

### 4.4 下载时的安全要求

- 创建任务时执行 `RealPath` 和文件类型校验，或者在任务开始时重新校验已保存的绝对路径；
- 任务开始时如果远端文件已被删除或变成目录，应失败并显示错误；
- 重试复用原任务的绝对远端路径，不重新根据当前 cwd 解析；
- 切换会话不会改变任务的 `sessionId`；
- 远端路径不能跨 session 或借用全局当前会话。

### 4.5 必须新增测试

1. 在 `/dir-a` 创建下载任务，确认 DTO 保存 `/dir-a/file.txt`；
2. 创建任务后将 session cwd 改为 `/dir-b`，执行任务仍读取 `/dir-a/file.txt`；
3. 排队任务重试后仍使用 `/dir-a/file.txt`；
4. 两个目录存在同名文件时，验证实际内容来自任务创建时的目录；
5. SftpPanel 测试断言 enqueueDownload 收到完整路径，而不是 `entry.name`。

## 5. P1 问题三：finalizing 阶段取消语义错误

### 5.1 问题位置

- [src/renderer/src/components/TransferCenter.tsx:277-293](E:/Projects/NodeShell/src/renderer/src/components/TransferCenter.tsx:277)
- [internal/sftpservice/sftpservice.go:1096-1104](E:/Projects/NodeShell/internal/sftpservice/sftpservice.go:1096)
- [internal/sftpservice/sftpservice.go:1210-1222](E:/Projects/NodeShell/internal/sftpservice/sftpservice.go:1210)
- [internal/sftpservice/transfer_manager.go:503-513](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:503)

### 5.2 根因

上传和下载在数据复制完成后发送 finalizing 进度：

```go
onProgress(total, total, true)
```

之后才执行最终提交：

- 上传：关闭远端临时文件并 rename/原子提交；
- 下载：flush、close、权限处理并原子替换本地目标。

但 TransferCenter 对 `finalizing` 仍显示取消按钮；`Cancel` 会调用 context cancel。底层提交过程没有始终检查 context，而 `runTask` 又先判断 `runErr == nil`：

```go
if runErr == nil {
    task.state = StateSucceeded
} else if ctx.Err() != nil {
    task.state = StateCancelled
}
```

因此取消发生在 finalizing 或返回前的窗口内时，任务仍可能提交文件并最终显示 succeeded。

### 5.3 产品语义必须固定

第一版不支持暂停/继续，但取消必须有确定语义：

- `queued`：可以立即取消，不启动；
- `running`：请求取消，停止读写并清理临时文件；
- `finalizing`：进入不可逆提交后，不再允许取消；界面显示“正在完成”；
- `succeeded`：文件已提交成功；
- `failed`：提交或传输失败；
- `cancelled`：未提交目标文件且临时文件已清理。

推荐将 finalizing 视为不可取消状态：

1. 后端进入 finalizing 时清空或禁用 cancel 函数；
2. 前端 finalizing 状态不显示取消按钮；
3. 前端显示“正在完成”状态；
4. 如果用户在按钮点击和状态切换之间发起取消，后端必须在提交前再次判断 context；
5. 一旦提交开始，不再伪装成取消，最终以 succeeded/failed 为准。

### 5.4 后端状态修复

至少需要做到：

```text
进入 finalizing 前检查 ctx.Err()
提交前检查 ctx.Err()
提交成功后即使 ctx 已取消，也必须按真实文件结果返回 succeeded
提交尚未开始且 ctx 已取消，必须清理临时文件并返回 context.Canceled
```

同时建议在 `runTask` 中明确状态优先级：

1. 如果底层已经成功提交，标记 succeeded；
2. 如果底层返回取消且未提交，标记 cancelled；
3. 其他错误标记 failed。

不能仅根据 `ctx.Err()` 覆盖一个已经成功提交的结果，也不能仅根据 `runErr == nil` 忽略已确认尚未提交的取消。

### 5.5 必须新增测试

1. running 阶段取消，任务为 cancelled，无目标文件和临时文件；
2. finalizing 开始前取消，任务为 cancelled；
3. 提交已经开始后取消，任务结果与实际文件一致，不出现“显示 cancelled 但文件已成功”的矛盾；
4. finalizing 状态的 UI 不显示可点击取消按钮；
5. 取消成功、取消失败和提交成功各只发一次终态事件；
6. 重试 cancelled 任务时生成新 taskId。

## 6. P2 问题：应用关闭没有等待传输结束

### 6.1 问题位置

- [internal/sftpservice/transfer_manager.go:399-426](E:/Projects/NodeShell/internal/sftpservice/transfer_manager.go:399)
- [app.go:377-403](E:/Projects/NodeShell/app.go:377)

### 6.2 根因

`TransferManager.Dispose()` 会设置 closed 并调用运行任务的 cancel，但没有等待任务 goroutine 退出。随后 `App.shutdown()` 继续：

1. 销毁 session；
2. 销毁 SFTP service；
3. Wails runtime 可能开始关闭。

运行中的 SFTP 协程可能仍在使用远端 client 或向 sink 发事件。

### 6.3 修复建议

1. TransferManager 增加 `sync.WaitGroup`；
2. 每个运行任务启动时 `Add(1)`，协程结束时 `Done()`；
3. `Dispose()` 取消所有排队和运行任务后，在有限超时时间内等待；
4. 超时后记录日志并继续关闭，不能无限阻塞应用退出；
5. `runTask` 在 manager closed 后不再向已销毁的 Wails sink 发送非必要事件；
6. 应用 shutdown 顺序保持为：TransferManager cancel/wait -> monitor/tunnel/agent -> session -> SFTP resource。

建议等待上限为 3 秒。超时不代表任务成功，必须记录未正常结束的任务数量，并确保临时文件清理由各传输函数的 defer 继续承担。

### 6.4 必须新增测试

1. Dispose 会取消所有运行任务；
2. Dispose 会等待 runner 返回；
3. runner 超时后 Dispose 能在有限时间内返回；
4. Dispose 后不会启动队列中的新任务；
5. Dispose 后任务不会重复发送终态事件。

## 9. 最终验收标准

修复 Agent 完成后，必须同时满足：

- 同一 taskId 的事件严格遵守合法状态转换；
- queued 不会覆盖 running、finalizing 或任何终态；
- 进度字节数单调递增且不超过 total；
- 下载任务保存创建时解析出的绝对远端路径；
- 切换会话或目录不会改变已入队任务的目标；
- finalizing 阶段取消行为与实际文件结果一致；
- cancelled 任务无不完整目标文件和临时文件；
- 应用退出会取消并等待传输任务，等待有明确上限；
- 每个任务的取消、重试、清除只作用于对应 taskId；
- 自动清理不会删除仍活跃的任务，也不会因状态回退而失效；
- 新增测试覆盖上述四类问题；
- 全量测试、类型检查、Lint、race 测试和生产构建通过；
- Windows 真实 Wails 构建完成多文件、多会话、切换目录、取消、重试和关闭应用验收。
