# 文件拖放上传与传输中心不可用：原因定位与修复计划

## 1. 结论

当前“文件拖入后不上传”和“传输中心无法正常打开”由两个独立的前端集成问题造成，不是 SFTP 任务调度器本身无法创建任务。

### P1：拖放事件被 React 阻断

项目已经调用 Wails 前端的 window.runtime.OnFileDrop，但 SFTP 区域的 React 拖放处理器在 dragover 和 drop 事件中调用 stopPropagation。Wails 2.13.0 的拖放监听器安装在 window 的冒泡阶段，因此事件到不了 Wails 的全局处理器，绝对路径解析和 files.onDrop 回调都不会发生。

故障链：

    文件拖到 .sftp-panel-body
      -> React handleDragOver / handleDrop 执行 stopPropagation()
      -> window.runtime.OnFileDrop 的 Wails window listener 收不到事件
      -> Wails 不调用 ResolveFilePaths
      -> files.onDrop 不触发
      -> TransferEnqueueUpload 不调用

### P1：传输中心浮层被父级 overflow 裁剪

传输中心组件挂载在 .session-tab-bar 内部，浮层使用 position: absolute 向下展开；但 .session-tab-bar 设置了 overflow: hidden。按钮本身可以渲染和改变 isOpen，实际浮层会被父级高度裁掉，因此用户看起来像是“传输中心打不开”。

故障链：

    点击 Transfers
      -> TransferCenter isOpen = true
      -> .transfer-center-popover 正常生成
      -> 父级 .session-tab-bar overflow:hidden
      -> 浮层超出 40px 标签栏区域的部分被裁剪
      -> 用户看不到任务面板

## 2. 代码证据

### 2.1 拖放事件阻断

SftpPanel.tsx 当前处理如下：

- handleDragOver 在第 320-325 行调用 e.stopPropagation()；
- handleDrop 在第 327-335 行调用 e.stopPropagation()，然后才执行本地 DOM fallback 判断；
- Wails 原生订阅在第 163-176 行通过 window.api.files.onDrop 接收路径。

bridge.ts 第 100-116 行已经正确调用 window.runtime.OnFileDrop，并传入 useDropTarget = true。因此本次不应继续修改 OnFileDrop 注册逻辑，真正的问题是事件无法冒泡到 Wails window listener。

Wails 2.13.0 的 OnFileDrop 会在 window 安装 dragover、dragleave、drop 监听，并从 drop 事件调用 ResolveFilePaths。项目 main.go 第 103-106 行的 EnableFileDrop = true 已满足能力开关，CSS 目标属性也已存在于 .sftp-panel-body。

### 2.2 浮层被裁剪

- TransferCenter 在 SessionTabs.tsx 第 121-134 行挂载在 .session-tab-bar-actions；
- .session-tab-bar 在 App.css 第 200-209 行设置固定高度 40px 并使用 overflow: hidden；
- 浮层在 App.css 第 3802-3817 行使用 position: absolute、top: calc(100% + 6px)，展开区域必然超出父级标签栏高度。

TransferCenter.tsx 第 88-156 行的 isOpen、任务查询和 region 渲染逻辑没有导致“打不开”的直接错误，主要是 CSS 裁剪。

## 3. 修复计划一：恢复 Wails 文件拖放链路

### 3.1 事件传播策略

修改 SftpPanel.tsx：

1. 移除 handleDragOver 中针对文件拖放的 stopPropagation；
2. 移除 handleDrop 中的 stopPropagation；
3. 保留 preventDefault，防止 WebView 默认打开文件或导航；
4. 保留 dataTransfer.dropEffect = copy；
5. 保留 window.api.files.onDrop 存在时跳过 DOM File.path fallback，避免一次拖放上传两次；
6. dragenter 和 dragleave 的视觉状态逻辑可以继续保留，但不要通过它们阻断 Wails 必需的 dragover 和 drop 冒泡。

推荐事件行为：

    dragover:
      React 更新拖放视觉状态
      preventDefault
      允许继续冒泡到 window
      Wails onDragOver 识别 --wails-drop-target

    drop:
      React 清除视觉状态
      preventDefault
      允许继续冒泡到 window
      Wails onDrop 解析绝对路径
      files.onDrop 回调入队上传

不要使用“React 先 stopPropagation，bridge 再主动触发 Wails ResolveFilePaths”的旁路方案。路径解析和坐标过滤应继续由 Wails 官方 runtime 负责。

### 3.2 处理 native 与 DOM fallback

当前适配策略应保持，但要明确事件传播不等于重复上传：

- Wails：files.onDrop 真实存在，Wails window listener 负责解析路径；React handleDrop 不走 File.path fallback；
- Electron：没有 Wails onFileDrop，React handler 允许事件继续冒泡，由 getPathForFile(file) 取得本地路径；
- 普通浏览器：无法取得绝对路径时显示现有 dropFilesOnly 错误。

如果担心 React handler 与 Wails handler 同时执行，必须依赖 native capability 判断抑制 fallback，而不是重新加回 stopPropagation。

### 3.3 Wails 目标区验证

修复后确认：

1. .sftp-panel-body 仍有 --wails-drop-target: drop；
2. OnFileDrop 使用 useDropTarget = true；
3. elementFromPoint(x, y) 落在 body 或继承该 CSS 属性的子节点上；
4. SFTP body 内部的 overlay 使用 pointer-events: none，不遮挡投放目标；
5. 文件拖到 SFTP 区域外不触发上传。

## 4. 修复计划二：让传输中心浮层可见

### 4.1 推荐方案：Portal 到 document.body

将 TransferCenter 的 popover 通过 React Portal 渲染到 document.body，使用 position: fixed 定位到入口按钮下方或窗口右上角。这样不受 .session-tab-bar 的 overflow、固定高度和 stacking context 影响。

实施要点：

1. 入口按钮继续保留在标签栏右上角；
2. 打开时通过 triggerRef.current.getBoundingClientRect() 计算位置；
3. 浮层使用 fixed 的 top/right 或 top/left；
4. 窗口 resize、滚动和缩放时重新计算位置；
5. 浮层打开期间保持与按钮一致的 aria-expanded；
6. Escape、点击外部、点击关闭按钮继续生效；
7. 浮层的 hover/focus 状态不能因 Portal 跨 DOM 树而失效。

推荐定位规则：

    right = max(12px, viewportWidth - triggerRect.right)
    top = triggerRect.bottom + 6px
    width = min(420px, viewportWidth - 24px)

### 4.2 可接受的替代方案

如果不采用 Portal，可以重构标签栏：

    .session-tab-bar
      .session-tab-list       // overflow:hidden，仅裁剪标签列表
      .session-tab-bar-actions // overflow:visible，容纳传输中心

不能简单地把 .session-tab-bar 的 overflow 全局改成 visible，否则标签过多时会破坏现有标签栏的裁剪和布局。

### 4.3 入口可用性

传输中心入口应在以下场景都存在并可点击：

- 没有 SSH 会话；
- 有一个或多个会话；
- SFTP 面板折叠；
- SFTP 面板未连接；
- 任务列表为空；
- 有 queued、running、finalizing 任务；
- 只有 succeeded、failed、cancelled 历史任务。

TransferCenter 不应依赖 SftpPanel 是否挂载，也不应在没有任务时隐藏入口。

## 5. 相关健壮性修复

### 5.1 事件顺序

TransferManager 当前在 transfer_manager.go 第 238 行调度任务后，才在第 241 行发送 queued 快照。运行协程可能先发送 running 或 succeeded，导致 queued 事件倒序到达。

应保证：

    queued -> running -> finalizing -> succeeded / failed / cancelled

并在前端 Hook 中拒绝终态回退和字节数回退。

### 5.2 finalizing 取消

TransferCenter 当前对 finalizing 仍展示取消操作。应明确 finalizing 是否可取消：推荐进入不可逆提交后禁用取消按钮，避免用户看到“已取消”但文件已经成功提交。

### 5.3 任务完成后的列表刷新

SftpPanel 当前按 sessionId 监听成功任务。刷新前还应校验任务目标目录是否仍是当前目录，避免用户切换目录后被旧任务完成事件打扰。

## 8. 最终验收标准

修复完成后必须满足：

- 文件拖入展开的 SFTP 文件区能触发一次上传任务；
- Wails native drop 的绝对路径能到达 TransferEnqueueUpload；
- React 拖放视觉反馈仍正常，且不阻断 Wails window listener；
- Electron fallback 不受影响，且不会与 native 路径重复上传；
- 传输中心入口始终可见、可点击；
- 点击入口后浮层实际显示，不被父级 overflow 裁剪；
- 浮层在窄窗口和不同缩放下不溢出；
- 任务与 SFTP 面板、当前会话和当前目录解耦；
- 每个文件由独立 taskId 管理；
- queued、running、finalizing 和终态事件不回退；
- 取消、重试、自动清理和任务操作仍按 taskId 工作；
- 自动化测试、race 测试、类型检查、Lint 和 Wails 构建通过；
- Windows 真实 Wails 构建完成拖放上传、传输中心打开、多文件和多会话验收。
