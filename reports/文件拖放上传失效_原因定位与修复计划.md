# 文件拖放上传失效：原因定位与修复计划

## 1. 结论

当前“把本地文件拖入 SFTP 文件区后没有上传”的直接原因已经从代码与 Wails 2.13.0 源码中确认：

1. NodeShell 后端调用了 Go 侧 `runtime.OnFileDrop`，但前端从未调用 Wails 浏览器侧的 `window.runtime.OnFileDrop`。
2. Wails 浏览器侧 `OnFileDrop` 才负责安装全局 `dragover`、`dragleave`、`drop` 监听器，并在 Windows WebView2 中调用 `ResolveFilePaths` 取得绝对路径。
3. NodeShell 的 React `handleDrop` 看到 `window.api.files.onDrop` 属性存在后会直接返回，以避免原生路径与 DOM 路径重复上传。
4. 因此前端原生路径没有启动，DOM 兜底又被无条件禁用，最终不会调用 `sftp.uploadPaths`，界面通常也不会显示错误。

故障链可简化为：

```text
没有调用 window.runtime.OnFileDrop
  -> Wails 未安装浏览器 drop 监听器
  -> 本地文件未解析为绝对路径
  -> Go runtime.OnFileDrop 收不到 wails:file-drop
  -> files:onDrop 不会发到 React

同时：
window.api.files.onDrop 始终是一个函数
  -> React DOM handleDrop 在第 365 行直接 return
  -> 没有兜底、没有上传、没有错误提示
```

这不是 SFTP 上传服务本身失败，而是文件在进入 `SftpUploadPaths` 之前就被丢失。

## 2. 当前实现链路

### 2.1 Wails 配置

`main.go:98-107` 已正确开启文件拖放：

```go
DragAndDrop: &options.DragAndDrop{
    EnableFileDrop:     true,
    DisableWebViewDrop: false,
},
```

- `EnableFileDrop: true`：允许 Wails 的文件路径解析流程。
- `DisableWebViewDrop: false`：允许 WebView 接收外部拖放；这不是当前故障原因。

### 2.2 Go 侧注册与转发

`app.go:299-319` 使用：

```go
runtime.OnFileDrop(ctx, func(x, y int, paths []string) {
    runtime.EventsEmit(ctx, "files:onDrop", map[string]any{"paths": paths})
})
```

该调用只通过 Wails 事件总线监听 `wails:file-drop`。它不会在 WebView 中安装 DOM 拖放监听器，也不会主动解析文件路径。

`ctx.Value("events")` 的保护判断不是主要原因。Wails 2.13.0 在开发和生产启动流程中都会将 `events` 写入传给 `OnStartup` 的 context；正常桌面启动时该判断成立。

### 2.3 前端 adapter

`src/renderer/src/api/adapter.ts:171-179` 将 `files.onDrop` 固定实现成对自定义事件 `files:onDrop` 的订阅：

```ts
onDrop: (cb) =>
  events.on<{ paths: string[] }>(IPC.filesOnDrop, (payload) => cb(payload.paths))
```

这里没有调用 Wails 的 `window.runtime.OnFileDrop`，所以 Wails 浏览器侧拖放功能从未启动。

### 2.4 SFTP 面板

`src/renderer/src/components/SftpPanel.tsx:191-205` 订阅 `window.api.files.onDrop`，收到路径后调用 `sftp.uploadPaths`。这一段在“确实收到绝对路径”时逻辑成立。

`src/renderer/src/components/SftpPanel.tsx:357-389` 的 DOM drop 处理包含：

```ts
if (window.api.files.onDrop) return
```

Wails adapter 始终提供该函数，因此 DOM 分支永远不会读取 `dataTransfer.files`，也不会显示 `dropFilesOnly` 错误。

### 2.5 拖放目标 CSS

`src/renderer/src/App.css:567-580` 在 `.sftp-panel-body` 上设置：

```css
--wails-drop-target: drop;
```

该语法与 Wails 2.13.0 一致。CSS 自定义属性会继承到子元素，因此当前“整个 SFTP panel body 是目标区”的写法有效，不是本次故障原因。

当前产品作用域是“已展开的 SFTP 文件区”，并不是终端窗口任意位置。若产品要求把文件拖到终端区或窗口任意位置也上传，需要另行确定目标会话、远端目录和误触规则，不能只扩大 CSS 选择器。

## 3. Wails 源码证据

项目锁定 `github.com/wailsapp/wails/v2 v2.13.0`。

### 3.1 Go `OnFileDrop` 只订阅事件

Wails `pkg/runtime/draganddrop.go:9-31` 的核心行为是：

```go
EventsOn(ctx, "wails:file-drop", callback)
```

没有浏览器监听器注册或路径解析逻辑。

### 3.2 JavaScript `OnFileDrop` 才启动拖放入口

Wails `internal/frontend/runtime/desktop/draganddrop.js:235-265` 执行：

```js
window.addEventListener('dragover', onDragOver)
window.addEventListener('dragleave', onDragLeave)
window.addEventListener('drop', onDrop)
EventsOn('wails:file-drop', cb)
```

同文件 `onDrop` 会在支持时执行：

```js
window.runtime.ResolveFilePaths(e.x, e.y, files)
```

NodeShell 没有调用这个 JavaScript API，故缺失了整条链路的入口。

### 3.3 Wails 会按 CSS 目标过滤回调

JavaScript `OnFileDrop` 默认 `useDropTarget = true`，回调前会使用 `document.elementFromPoint(x, y)`，检查元素计算样式中的 `--wails-drop-target: drop`。NodeShell 已为 SFTP body 设置该属性，因此修复时应继续传入 `true`。

## 4. 为什么现有测试没有发现

### 4.1 UI 测试绕过了真正入口

`tests/ui/sftp.test.tsx:175-203` 从 mock 中直接取出回调并手动执行：

```ts
const nativeDrop = fake.mocks.files.onDrop.mock.calls[0][0]
nativeDrop(['C:\\local\\a.txt'])
```

它只证明“若路径已经到达组件，组件会上传”，没有证明 Wails runtime 注册、路径解析或事件传递能够发生。

### 4.2 adapter 测试只模拟自定义事件

`tests/api-adapter.test.ts:346` 附近通过测试 bridge 直接发出 `files:onDrop`。该测试同样绕过 `window.runtime.OnFileDrop`，因此会在生产功能完全失效时继续通过。

### 4.3 当前测试固化了失效条件

UI 测试明确要求：只要 `files.onDrop` 属性存在，就必须禁止 DOM fallback。它没有区分“API 属性存在”和“原生 drop runtime 已成功注册”。这使接口形状被误当成运行能力。

## 5. 推荐修复方案

采用“前端直接使用 Wails 官方拖放 API”的单链路方案。不要仅添加一个空的前端 `OnFileDrop` 再继续由 Go 转发，因为那会形成浏览器 -> Go 事件 -> Go 自定义事件 -> 浏览器的无必要往返，并增加重复投递和生命周期问题。

### 5.1 扩展 Wails bridge runtime 类型

修改 `src/renderer/src/api/bridge.ts`：

1. 在 `WailsRuntime` 中声明：

```ts
OnFileDrop?: (
  callback: (x: number, y: number, paths: string[]) => void,
  useDropTarget?: boolean
) => void
OnFileDropOff?: () => void
```

2. 在 bridge 能力中增加专用的 `onFileDrop` 方法，内部调用：

```ts
runtime.OnFileDrop((_x, _y, paths) => cb(paths), true)
```

3. 返回幂等 unsubscribe，并在解除订阅时调用 `runtime.OnFileDropOff()`。
4. runtime API 不存在时，不应假装注册成功；返回明确的“能力不可用”结果，供 adapter 决定是否启用 DOM fallback。

注意：Wails 的 `OnFileDrop` 内部是单例注册，重复调用会直接返回。bridge 必须明确单订阅所有权，避免多个组件分别注册后互相 `Off`。当前仅 SFTP 面板需要它，可保持单消费者；若未来扩展全窗口拖放，应提升为应用级 drop manager。

### 5.2 adapter 改用原生 runtime

修改 `src/renderer/src/api/adapter.ts`：

1. `files.onDrop` 改为 bridge 的 Wails `OnFileDrop` 封装。
2. 不再把自定义 `IPC.filesOnDrop` 作为文件拖放入口。
3. 明确区分“原生能力可用”和“函数字段存在”，避免再次出现假能力。

建议将 API 设计为能表示注册结果，例如：

```ts
onDrop: (cb: (paths: string[]) => void) => (() => void) | undefined
```

或由 adapter 构建时仅在 runtime 能力真实存在时暴露 `onDrop`。具体选择需遵循现有 `WindowApi` 初始化方式，但不得继续用永远存在的 no-op 订阅冒充原生支持。

### 5.3 删除 Go 中转链路

修改 `app.go`：

1. 删除 `filesOnDropEvent`。
2. 删除 `registerFileDrop`。
3. 删除 `startup` 中的 `a.registerFileDrop(ctx)`。
4. 若 `runtime` import 没有其他用途，清理 import；需先搜索确认。

修改 `main.go` 中的注释，使其说明 `EnableFileDrop` 配合前端 Wails runtime 使用，避免后续维护者再次误认为 Go 注册会自动启动 WebView drop。

修改 `src/shared/types.ts`：若 `IPC.filesOnDrop` 已无调用方，删除该常量及相关注释；若因兼容性暂时保留，标记 deprecated 并建立后续移除任务。

### 5.4 调整 SftpPanel 的兜底判断

保留当前“原生路径与 DOM 路径不能同时上传”的原则，但判断必须基于原生订阅是否成功，而不是属性是否存在。

推荐方案是 adapter 层保证：

- Wails runtime 可用：只走 `OnFileDrop`，DOM handler 仅负责视觉状态和阻止默认导航。
- Electron/支持 `File.path` 的宿主：不暴露原生 Wails onDrop，走 DOM `getPathForFile`。
- 普通浏览器：无法取得绝对本地路径时显示清晰错误，不静默返回。

不要同时从 Wails 原生回调和 DOM `File` 两路调用 `uploadPaths`，否则一次放置可能上传两次。

### 5.5 保留目标区域

本次按现有交互保留 `.sftp-panel-body { --wails-drop-target: drop; }`，不把目标扩大到整个窗口。验收文案应明确要求用户展开 SFTP 面板并拖入文件列表区域。

如后续确定“整个窗口都能投放”，应单独设计：

- 活动 SSH/SFTP 会话的选择规则；
- 远端目标目录规则；
- 面板折叠时的反馈；
- 多会话切换瞬间的归属；
- 终端文本拖放与文件拖放的冲突。

## 6. 测试计划

### 6.1 bridge 单元测试（必须新增）

Mock `window.runtime.OnFileDrop` 与 `OnFileDropOff`，验证：

1. 订阅时调用 `OnFileDrop(callback, true)`。
2. Wails 回调中的 `paths` 原样传给业务 callback。
3. `x/y` 不进入业务 API。
4. unsubscribe 调用 `OnFileDropOff`，且重复 unsubscribe 只执行一次。
5. 缺少 `OnFileDrop` 时明确报告不支持，不返回伪成功订阅。
6. 空路径数组不触发上传（可在 adapter 或组件层保证）。

### 6.2 adapter 测试（必须修改）

1. 删除或改写依赖 `bridge.emit('files:onDrop', ...)` 的测试。
2. 验证 `files.onDrop` 实际委托给 bridge 原生 drop API。
3. 验证退化环境选择 DOM fallback。
4. 验证一次 native drop 只交付一次。

### 6.3 SftpPanel 测试（必须修改）

1. 保留“收到绝对路径后调用当前 session 的 `uploadPaths`”测试。
2. 原生订阅成功时，DOM drop 不应造成第二次上传。
3. 原生能力不可用且 `File.path` 可用时，DOM drop 应上传。
4. 两种能力都不可用时，应显示错误，不能静默结束。
5. 面板卸载及 session 切换时正确解除旧订阅。
6. drop 回调发生在会话切换后时，只能使用投放瞬间的活动会话，不能上传到旧会话。

### 6.4 Go 测试

删除 Go 中转后，删除对应注册逻辑测试（若修复分支新增过）。SFTP 服务现有路径上传测试继续保留，它们验证的是后半段能力。

## 7. 桌面端人工验收

单元测试无法模拟 WebView2 的 `postMessageWithAdditionalObjects`，必须至少在 Windows 的真实 Wails 构建中验收。

### P0：核心流程

1. 启动真实 Wails 应用，不使用普通浏览器 Vite 页面代替。
2. 建立支持 SFTP 的 SSH 会话并展开 SFTP 面板。
3. 从资源管理器拖一个普通文件到 SFTP 文件列表区域。
4. 拖入时出现现有投放遮罩，放下后只上传一次。
5. 远端列表刷新，文件内容及大小正确。
6. DevTools/应用日志无 runtime 注册错误。

### P0：边界与安全

1. 拖到 SFTP 区域外不上传。
2. 未连接、无 session、SFTP 面板折叠时不上传。
3. 快速切换会话后投放，文件进入投放时当前会话，不进入旧会话。
4. 上传失败时显示错误，不能静默失败。
5. 一次拖入多个文件，各文件只上传一次。

### P1：兼容性

1. 文件名包含中文、空格、`#`、括号时可上传。
2. 大文件有正常进度，不阻塞 UI。
3. 目录拖放按产品当前规则处理；若后端不支持目录，应显示可理解的错误。
4. 在 macOS/Linux 构建可用时分别实机验证，因为路径解析机制与 Windows WebView2 不同。

## 8. 验收标准

满足以下条件才算修复完成：

- 真实 Wails 窗口中，拖入 SFTP 区域的文件能稳定调用一次 `SftpUploadPaths`。
- 不再依赖 Go `runtime.OnFileDrop` + 自定义 `files:onDrop` 的中转链路。
- 前端确实调用并清理 `window.runtime.OnFileDrop`。
- 不支持原生路径解析时有可预测的 fallback 或可见错误，不再静默返回。
- 拖放目标仍限制在当前约定的 SFTP 文件区。
- 多会话场景不会上传到错误 session。
- bridge、adapter、SftpPanel 三层测试覆盖真实注册契约，而非只手工调用 mock callback。
- `typecheck`、`lint`、前端测试、Go 测试和 Wails 构建全部通过。

## 9. 风险与实施顺序

建议按以下顺序修复：

1. 先为 bridge 的 `OnFileDrop/Off` 契约补失败测试。
2. 实现 bridge 原生订阅并让测试通过。
3. adapter 切换到新 bridge API。
4. 修正 SftpPanel 对“能力存在/注册成功”的判断。
5. 删除 Go 中转、自定义 IPC 和过时注释。
6. 跑完整自动化测试。
7. 使用真实 Windows Wails 包执行人工验收。

主要风险是 Wails drop 注册为全局单例。修复 Agent 不应在多个组件中各自调用 `OnFileDrop`；如果需求扩展为全窗口或多个投放区，应先建立应用级单一注册器，再根据坐标/目标元素和当前会话分发。
