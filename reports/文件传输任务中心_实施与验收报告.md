## 1. 背景与改造目标

在原实现中，SFTP 文件的上传与下载操作紧密绑定于 `SftpPanel` 组件的本地 React 状态。该模式存在以下关键痛点：
1. **生命周期耦合**：用户切换终端会话标签、折叠 SFTP 面板或在 SFTP 内切换目录时，组件卸载或状态重置会导致进度丢失或传输中断感知断裂；
2. **缺乏并发调度**：多文件同时操作时缺乏全局与单会话的排队与流控，容易抢占 SSH 信道或造成网络拥塞；
3. **不可取消与清理缺失**：传输过程中无法主动中断；若网络异常中断，远端/本地易残留无意义的半传输脏文件；
4. **单任务无排队反馈**：顶部标题栏仅能展示单一传输 Badge，无法查看历史/已完成任务列表、速率、剩余时间（ETA）或重试失败任务。

本次实施构建了**全局独立、单文件粒度、具备并发调度与 context 级实时中断**的全局文件传输任务中心（TransferCenter）。

## 2. 验收问题定位与完整修复

针对《文件拖放上传与传输中心不可用_原因定位与修复计划.md》以及《文件传输任务中心_验收问题修复报告.md》中指出的关键缺陷与集成风险，进行了全面彻底的修复：

### 2.1 [P1 修复] 恢复 Wails 文件拖放事件冒泡链路
- **根因分析**：
  - Wails 2.13.0 原生拖放机制依赖安装在 `window` 上的原生拖放事件监听器（冒泡阶段），在收到 `drop` 事件时通过 `ResolveFilePaths` 解析得到操作系统的绝对文件路径；
  - `SftpPanel.tsx` 在 `handleDragEnter`、`handleDragLeave`、`handleDragOver` 与 `handleDrop` 中调用了 `e.stopPropagation()`，阻断了事件冒泡至 `window`，导致 Wails 永远无法接收到拖放事件，`files.onDrop` 回调无法被触发。
- **修复措施**：
  - 移除 `SftpPanel.tsx` 拖放事件中的 `e.stopPropagation()`，仅保留 `e.preventDefault()` 防止浏览器默认导航/打开文件行为与 `dropEffect = 'copy'`；
  - 允许事件顺畅冒泡至 `window`，Wails 原生文件绝对路径解析与 `files.onDrop` 顺利触发并调用 `window.api.transfer.enqueueUpload`；
  - 维持 `window.api.files.onDrop` 存在时跳过 DOM File.path fallback 的逻辑，杜绝重复上传。

### 2.2 [P1 修复] 传输中心浮层使用 React Portal 渲染（避免父级 overflow 裁剪）
- **根因分析**：
  - `<TransferCenter />` 挂载在 `.session-tab-bar-actions` 中，父级 `.session-tab-bar` 设置了 `height: 40px; overflow: hidden;`；
  - 原浮层使用 `position: absolute; top: calc(100% + 6px);`，展开后超出 40px 的内容被父容器裁剪，导致用户点击后“看似打不开”。
- **修复措施**：
  - 将 `.transfer-center-popover` 改为使用 **React Portal (`createPortal(..., document.body)`)** 渲染至 `document.body`；
  - 通过 `triggerRef.current.getBoundingClientRect()` 动态计算 fixed 定位（`top = rect.bottom + 6`，`right = Math.max(12, window.innerWidth - rect.right)`，`maxWidth = Math.min(420, window.innerWidth - 24)`）；
  - 监听 `window` 的 `resize` 和 `scroll` 事件实时自适应重新定位；
  - 在 `App.css` 中将 `.transfer-center-popover` 样式调整为 `position: fixed; z-index: 10000;`；
  - 浮层展开/关闭、点击外部检测、Escape 快捷键关闭以及测试完全正常生效。

### 2.3 [P1 修复] 任务状态事件严格保序与前端防回退
- **后端根因修复**：
  - 重构 `TransferManager` 任务入队与调度流水线：`EnqueueUpload`、`EnqueueDownload`、`Retry` 在加锁阶段创建任务，解锁后**优先发送 `queued` DTO 事件**，然后再执行 `schedule()`；
  - `schedule()` 在主线程中更新 `running` 状态并生成 `running` DTO，先向 sink 发送 `running` DTO，再启动执行 goroutine；
  - 彻底杜绝了快速传输小文件时 `running` 或 `succeeded` 事件先于 `queued` 事件到达导致的状态乱序问题（严格保障 `queued -> running -> (finalizing ->) succeeded/failed/cancelled` 顺序）。
- **前端防御机制**：
  - `useTransferTasks` 引入 `STATE_RANK` 状态等级权重与 `isTerminalState` 判定；
  - 当本地任务已达到终态（`succeeded`/`failed`/`cancelled`）时，任何迟到的非终态事件直接丢弃；
  - 同一状态下若收到较小的 `transferred` 进度字节，自动保留最大单调递增值，防止进度条抖动。

### 2.4 [P1 修复] 排队下载远端路径绝对化与 CWD 隔离
- **根因与修复**：
  - 在 `SftpPanel.tsx` 中，`handleDownload` 传入 `entry.path`（绝对远端路径，如 `/home/user/docs/readme.md`）而非相对文件名；
  - 在 `app.go` 中，新增 `resolveAbsoluteRemotePath` 辅助函数，在任务创建入队时即刻解析为绝对路径并固化于 `Task.remotePath`；
  - 在 `sftpservice.go:DownloadWithContext` 中，优先使用绝对路径，不随用户后续在 SFTP 浏览面板中切换目录而发生漂移；重试时同样沿用固化的绝对路径。

### 2.5 [P1 修复] Finalizing 阶段确定性取消语义
- **交互与后端对齐**：
  - 数据拷贝完成后进入 `finalizing` 阶段（原子提交与重命名），此阶段为不可逆操作；
  - 前端 `TransferCenter.tsx` 在 `finalizing` 状态下**隐藏取消按钮**，状态展示为“正在完成 (Finalizing)”；
  - `TransferManager.Cancel(taskID)` 对 `finalizing` 状态直接返回且不触发 context cancel；
  - 后端 `UploadWithContext` 与 `DownloadWithContext` 在执行原子提交/替换前增加 `ctx.Err()` 检查，确保提交开始前已被取消的任务不会提交残破文件，已开始提交成功的任务严格返回 `succeeded`。

### 2.6 [P2 修复] 应用关闭优雅等待 (WaitGroup & 超时控制)
- **优雅退出流程**：
  - `TransferManager` 增加 `sync.WaitGroup` 追踪所有在途执行协程；
  - `Dispose()` 时首先置位 `closed = true`，取消所有运行任务并设置排队任务为 `cancelled`；
  - 随后在 3 秒有限超时内等待活跃协程执行完毕并清理临时文件；
  - `runTask` 在 manager 关闭后静默退出，不再向已销毁的 Wails sink 发送事件。

## 5. 人工验收操作指南

测试人员可按照以下步骤对文件传输任务中心与拖放功能进行全流程核验：

### 5.1 文件拖放上传核验（针对修复一）
1. 连接一个 SSH 会话并展开底部的 SFTP 文件面板；
2. 打开 Windows 资源管理器，将一个或多个文件拖入 SFTP 列表区域；
3. 观察拖放视觉反馈正常呈现（边框高亮与拖放提示）；
4. 松开鼠标，Wails `files.onDrop` 正常接收绝对路径并入队；
5. 标签栏右上角传输中心徽标数值增加，对应文件开始上传。

### 5.2 传输中心浮层显示与交互核验（针对修复二）
1. 点击标签栏右上角“传输任务”按钮；
2. 浮层通过 Portal 正常弹出显示在右上角下方，**不被标签栏高度裁剪**；
3. 浮层展示任务名称、会话名、传输进度、速度及 ETA；
4. 点击关闭按钮、点击窗口空白处或按 `Escape` 键，浮层顺利关闭；
5. 调整窗口大小或缩放比例，浮层位置始终紧随右上角对齐。
