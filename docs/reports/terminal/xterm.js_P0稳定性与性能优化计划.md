# xterm.js P0 稳定性与性能优化计划

## 1. 目标

在继续使用 `xterm.js + Wails + Go SSH PTY` 的前提下，优先解决终端在多会话、高速输出和窗口布局变化时可能出现的状态丢失、输入延迟、卡顿、尺寸抖动和远程终端尺寸不一致问题。

本阶段只做稳定性和性能基础治理，不更换 Ghostty，不新增终端高级功能，不重做 SSH 会话架构。

## 2. 当前实现基线

- `TerminalView` 为每个 SSH 会话创建一个独立 `Terminal` 实例。
- 使用 `FitAddon` 计算列数和行数。
- 尝试启用 `WebglAddon`，失败时保留 xterm.js DOM 渲染。
- 使用 `UnicodeGraphemesAddon` 改善组合字符和宽字符处理。
- 每个终端使用 `scrollback: 1000`。
- Go 侧通过 `outputBatcher` 以约 `12ms` 或 `48KB` 为边界合并 PTY 输出。
- 前端再使用 `requestAnimationFrame` 合并输出后调用 `term.write`。
- `ResizeObserver` 触发 fit，当前使用约 `80ms` 延迟合并后调用远程 `sessions.resize`。
- 多会话切换时保留已创建的终端实例，后台输出直接写入对应会话；未挂载时使用有上限的输出环缓存。

相关文件：

- `src/renderer/src/components/TerminalView.tsx`
- `src/renderer/src/components/SessionTabs.tsx`
- `src/renderer/src/hooks/useSessions.ts`
- `internal/sessions/batcher.go`
- `internal/sessions/sessions.go`
- `internal/sshclient/sshclient.go`

## 3. P0 问题范围

### 3.1 输出链路积压

当前输出已经经过后端批处理和前端动画帧合并，但缺少端到端的积压观测和明确策略。高速执行 `yes`、日志刷屏、编译或大批量 ANSI 输出时，需要确认：

- Wails 事件发送速度是否超过前端消费速度。
- 前端 `pending` 字符串是否持续增长。
- `term.write` 是否出现长队列。
- 输出延迟是否会影响用户键盘输入。
- 关闭会话时是否还有未处理输出。

### 3.2 resize 重复与布局抖动

侧栏、SFTP 区域、窗口或字体变化会触发 `ResizeObserver`。当前每次执行 fit 后都会调用远程 resize，可能产生重复的 `WindowChange`：

- 同一个 `cols/rows` 被重复发送。
- 布局动画期间连续发送多个中间尺寸。
- 终端本地尺寸和远程 PTY 尺寸短时间不一致。
- 远程程序在频繁 resize 下重绘，造成闪烁或状态变化。

### 3.3 多会话生命周期

当前通过保留多个 `Terminal` 实例解决了切换清屏问题，但需要继续保证：

- 切换会话不会 dispose 非当前终端。
- 后台会话持续接收输出。
- 会话关闭只销毁对应终端。
- 连接中的临时会话不会创建错误的终端实例。
- 切换、关闭和重连竞争时不会把输出写入错误会话。

### 3.4 高负载和异常场景缺少指标

现有测试覆盖多会话持久性，但还应补充高速输出、resize 合并、WebGL 降级和资源清理验证，避免只验证“功能能用”而无法发现性能回归。

## 4. 实施方案

### 4.1 输出队列治理

修改 `TerminalView.tsx` 和必要的会话输出适配代码：

1. 保留当前“每动画帧最多写入一次”的合并方式，避免退回到每个 IPC chunk 调用 `term.write`。
2. 为前端 pending 输出增加可观测的长度和处理耗时指标，开发模式或测试环境可记录，生产环境避免输出敏感内容。
3. 明确队列上限策略：正常情况下不得丢弃终端输出；达到异常上限时应记录告警并采取可解释的降级措施，不能静默截断。
4. 使用 xterm.js 的异步写入完成回调或等价机制观察渲染积压，避免在消费未完成时无限追加任务。
5. 会话关闭时正确清理 RAF、pending 数据和事件监听，区分正常尾部 flush 与关闭时丢弃数据。
6. 后端继续保留 `outputBatcher` 的 UTF-8 边界处理，禁止为追求吞吐而破坏 ANSI/UTF-8 字节顺序。

需要先通过基准测试确定批处理参数是否需要调整，不直接凭感觉修改 `12ms` 和 `48KB`。

### 4.2 resize 去重和布局稳定

修改 `TerminalView.tsx` 以及侧栏/SFTP 布局动画完成后的同步时机：

1. 每个终端缓存最近一次已发送的 `cols/rows`。
2. fit 后只有尺寸真正变化时才调用 `window.api.sessions.resize`。
3. 同一事件循环或短时间窗口内的多次 ResizeObserver 回调只保留最后一次尺寸。
4. 侧栏、SFTP 和窗口动画期间优先完成本地布局，动画结束后再发送最终远程尺寸；如果无法取得动画结束事件，则使用稳定帧或防抖窗口。
5. Tab 切换仍需快速 fit，但也必须经过尺寸去重。
6. 字体变化、主题变化和终端首次打开分别处理，不让主题更新触发无意义的远程 resize。
7. `cols/rows` 必须始终为正整数，远程 resize 失败时记录错误但不能销毁终端实例。

### 4.3 多会话实例与输出路由

保持当前架构，不把所有会话改成单例终端：

- `TerminalView` 的 React `key` 继续使用稳定的 `sessionId`。
- 非当前会话继续保持实例和终端状态，避免切换清屏。
- `useSessions` 的数据监听器按 `sessionId` 路由，禁止使用当前激活会话作为输出路由依据。
- 终端销毁时解除对应 listener、取消 RAF 和 ResizeObserver。
- 会话关闭、重连和连接失败时清理对应输出环，不能影响其他会话。
- 如未来引入虚拟化或卸载后台终端，必须先设计完整终端状态恢复方案，不能只依靠有限输出环恢复全部屏幕状态。

### 4.4 WebGL 与 DOM 降级

保留当前 WebGL 优先、DOM 降级策略，并补充：

- WebGL context loss 后确认 xterm 仍能继续写入和交互。
- WebGL 不可用时不重复尝试造成性能抖动。
- 记录 renderer 类型，便于定位不同机器上的性能差异。
- 不将 WebGL 是否启用作为功能正确性的前置条件。
- 在 Windows WebView2 环境下验证 GPU、远程桌面和禁用硬件加速场景。

## 5. 测试计划

### 5.1 组件测试

新增或更新 `TerminalView` 和会话持久性测试，覆盖：

- 多个会话分别收到输出，不能串到当前激活会话。
- 切换 Tab 不创建新实例、不 dispose 旧实例、不清空终端内容。
- 关闭一个会话只销毁对应终端。
- 快速切换、关闭和重连期间 listener 与实例保持一致。
- 相同 `cols/rows` 不重复调用远程 resize。
- 不同尺寸最终只发送最新有效尺寸。
- 组件卸载后 RAF、ResizeObserver 和输出监听均被清理。
- WebGL 加载失败或 context loss 后仍可写入输出。

### 5.2 后端测试

保持并扩展 `internal/sessions` 测试：

- 输出批处理在高频 stdout/stderr 下保持顺序。
- UTF-8 多字节字符跨 chunk 时不产生错误替换字符。
- 达到字节阈值和定时 flush 时不会重复或丢失数据。
- Close、Discard 与 Add 并发时不会泄漏 timer 或晚发事件。
- 多会话输出事件的 `sessionId` 始终正确。

### 5.3 高负载手工/自动验证

至少验证以下命令或等价场景：

- `yes`
- 大量 ANSI 彩色输出
- 长时间日志滚动
- 编译项目产生的连续输出
- 中文、Emoji、组合字符和宽字符混合输出
- 侧栏和 SFTP 面板连续展开/收起
- 多会话同时产生后台输出并反复切换

记录以下指标：

- 首字节到屏幕显示延迟
- 键盘输入响应延迟
- pending 输出峰值
- `term.write` 调用次数和单次写入大小
- resize 调用次数及重复比例
- WebGL/DOM renderer 类型
- 内存是否随持续输出无界增长

## 6. 验收标准

### 稳定性

- 多会话连续切换不会清屏、串屏或丢失已显示内容。
- 后台输出持续进入正确会话，切换回来后状态完整或符合明确的滚动历史上限。
- 关闭、重连和应用退出后没有残留输出监听、RAF、定时器或 ResizeObserver。
- UTF-8、ANSI、备用屏幕和常规交互不因批处理而改变行为。

### 性能

- 正常输出场景下前端 pending 队列能够持续排空，不会单调增长。
- 高速输出时 UI 不出现持续冻结，键盘输入仍能在可接受延迟内发送。
- 相同终端尺寸不重复调用远程 resize。
- 侧栏或 SFTP 动画不会导致远程 PTY 高频 resize。
- 长时间输出不会出现无法解释的内存持续增长。

### 兼容性

- WebGL 可用、WebGL 不可用、WebGL context loss 三种环境都能使用终端。
- Windows WebView2、远程桌面和不同 DPI 缩放下列数/行数正确。
- 现有主题、字体大小、复制、粘贴、清屏和右键菜单行为不回归。
- `prefers-reduced-motion` 下不引入额外布局抖动。

## 7. 实施顺序

1. 建立输出吞吐、resize 次数和多会话切换的现有基线。
2. 完成 resize 去重和最终尺寸同步，这是最容易影响远程 PTY 的改动。
3. 完成前端输出队列观测与消费治理。
4. 核对多会话 listener、RAF、ResizeObserver 和 dispose 生命周期。
5. 补充 WebGL/DOM 降级和高负载测试。
6. 进行长时间运行、连续切换和窗口布局变化验收。
7. 执行项目类型检查、全部测试和 Wails 前端构建。

## 8. 风险与控制

- **输出被误截断**：P0 不允许直接丢弃正常终端输出；任何上限策略必须有测试、日志和明确的产品决策。
- **resize 延迟过大**：本地终端先完成 fit，远程只延迟发送最终稳定尺寸；交互输入不应等待 resize 完成。
- **改变终端行为**：不修改 `TERM=xterm-256color`、SSH PTY 协议和 Go 侧输入输出语义。
- **性能指标干扰**：生产环境只记录计数和耗时，不记录终端内容、密码或敏感命令输出。
- **多会话回归**：任何生命周期改动都必须通过已有 `session-terminal-persistence` 测试和后台输出路由测试。
- **调整批处理参数导致体验变化**：先基准测试，再小幅修改，并保留回退参数。

## 9. 非目标

- 不迁移到 Ghostty 或其他终端引擎。
- 不在 P0 中增加搜索、链接识别、终端录制、分屏或新终端菜单。
- 不改变 SSH、SFTP、端口映射和 Agent 业务逻辑。
- 不将有限输出环伪装成完整终端快照持久化方案。
- 不为了性能直接禁用 WebGL 或删除当前 DOM 降级能力。
