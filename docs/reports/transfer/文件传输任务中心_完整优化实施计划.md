# 文件传输任务中心：完整优化实施计划

## 1. 需求确认

本计划针对当前 SFTP 文件上传、下载进度体验不足的问题，目标是建设一个与 SFTP 面板生命周期分离的全局传输任务中心。

已确认的产品决策：

- 传输中心采用独立的应用内弹窗/浮层，不创建操作系统级第二窗口。
- 入口固定在主窗口右上角，支持随时展开和收起。
- 传输任务与 SFTP 面板分离；折叠 SFTP、切换会话或切换 SFTP 目录时，任务继续执行并保持可见。
- 每个文件单独显示任务，不用一个总进度覆盖多个文件。
- 全局并发最多 3 个，同一 SSH 会话最多 1 个，其余任务排队。
- 第一版支持取消和重试，不支持暂停/继续；断点续传留到下一版。
- 任务完成后自动消失，但成功、取消、失败采用不同保留时间。

## 2. 当前问题定位

### 2.1 前端只有一个进度状态

`src/renderer/src/components/SftpPanel.tsx` 当前使用单个：

```ts
const [transfer, setTransfer] = useState<SftpTransferProgressEvent | null>(null)
```

任何新的上传或下载事件都会覆盖前一个任务。批量上传、同时下载多个文件、同名文件跨会话传输时，用户无法知道每个文件的真实状态。

### 2.2 进度事件没有稳定任务标识

当前 `SftpTransferProgressEvent` 只有：

- `sessionId`
- `direction`
- `name`
- `transferred`
- `total`
- `done`

没有 `taskId`、任务状态、错误信息、排队时间和完成时间。前端无法可靠更新某一个文件，也无法实现取消、重试和历史清理。

### 2.3 后端批量上传是串行调用

`internal/sftpservice/sftpservice.go:784-815` 的 `UploadPaths` 会依次调用 `Upload`。这本身适合控制同一会话的 SFTP 稳定性，但目前没有任务队列，因此队列中的文件不会被单独展示，也不能取消某个排队项。

### 2.4 传输过程没有取消控制

当前上传和下载使用 `io.Copy`，传输函数没有 `context.Context` 或任务取消信号。UI 即使增加“取消”按钮，也无法让底层网络读写停止，只能伪装成取消。

### 2.5 进度信息不足且不稳定

现有事件只提供已传字节和总字节，未提供：

- 速度；
- 剩余时间；
- 明确的排队、完成、失败、取消状态；
- 任务错误原因；
- 任务所属会话名称和目标目录。

后端当前按约 80ms 节流事件，但前端没有时间窗口平滑和异常值处理，直接显示瞬时百分比会造成跳动。

### 2.6 完成状态可能提前或无法区分

上传在字节复制完成后还要关闭远端文件并执行临时文件到目标文件的提交；下载还要 flush、close 和原子替换。传输字节达到 100% 不等于任务已最终成功，因此需要将“数据传输完成”和“任务成功”区分开。

## 3. 总体架构

采用“后端任务调度器 + 全局前端任务中心”的双层架构。

```text
用户点击上传/下载或拖放文件
        |
        v
App 创建任务，固定 session、远端目录和文件信息
        |
        v
TransferManager 全局排队
  - 全局并发 <= 3
  - 同一 session 并发 <= 1
  - 队列、取消、重试
        |
        v
SFTP Service 使用 context 执行单文件传输
        |
        v
结构化 TransferEvent(taskId, state, bytes, speed, eta, error)
        |
        v
全局 TransferCenter 订阅并渲染任务列表
```

### 3.1 任务的单一事实来源

后端任务管理器负责传输任务的真实状态，前端只负责展示、计算显示层平滑数据和发起操作。不能让 SftpPanel 和 TransferCenter 各自维护一份上传状态。

### 3.2 单文件任务模型

批量选择或批量拖放时，先拆成多个文件任务。每个任务有独立的 `taskId`，即使文件名相同也不能复用 ID。

建议任务数据结构：

```ts
type TransferDirection = 'upload' | 'download'
type TransferState = 'queued' | 'running' | 'finalizing' | 'succeeded' | 'failed' | 'cancelled'

interface TransferTask {
  taskId: string
  sessionId: string
  sessionTitle: string
  direction: TransferDirection
  name: string
  sourcePath?: string
  remotePath: string
  localPath?: string
  transferred: number
  total: number
  state: TransferState
  error?: string
  createdAt: number
  startedAt?: number
  finishedAt?: number
  retryOf?: string
}
```

不建议把本地绝对路径完整发送到 UI 任务列表或错误文本中；显示名称即可，后端内部保存执行所需路径。远端目录和本地目标目录应按现有安全边界校验。

## 4. 后端实施计划

### 4.1 建立 TransferManager

建议新增 `internal/transfer` 或 `internal/sftpservice/transfer_manager.go`，具体目录遵循当前项目的模块边界。管理器至少维护：

- `tasks map[taskID]*Task`；
- FIFO 等待队列；
- 每个 session 的运行计数；
- 全局运行计数；
- 每个任务的 `context.CancelFunc`；
- 任务状态和完成时间；
- 任务事件 sink。

任务启动条件：

```text
globalRunning < 3
and sessionRunning[sessionId] == 0
```

不满足条件的任务保持 `queued`。调度器在任务结束、取消或新任务加入时尝试填充可运行槽位。

### 4.2 固定任务上下文

任务创建时必须固定以下信息：

- `sessionId`；
- 会话显示名称；
- 上传时的远端当前目录；
- 下载时的远端文件路径；
- 下载时用户选择的本地目标路径；
- 上传源文件的 basename；
- 创建时的总大小。

不能在任务真正开始时重新读取当前 SFTP 面板目录，也不能从全局当前会话推导任务归属。这样可以避免用户入队后切换会话或目录导致文件传到错误位置。

### 4.3 新增任务 API

建议在 `App` 和共享 API 中增加以下能力，命名按现有 `Sftp*` 风格调整：

```ts
enqueueUpload(sessionId: string, remoteDir: string, localPaths: string[]): Promise<string[]>
enqueueDownload(sessionId: string, remotePath: string, localPath: string): Promise<string>
cancelTransfer(taskId: string): Promise<void>
retryTransfer(taskId: string): Promise<string>
clearTransfer(taskId: string): Promise<void>
clearCompletedTransfers(): Promise<void>
onTransferTask(cb: (event: TransferTaskEvent) => void): () => void
```

建议再提供 `getTransferTasks()`，用于前端启动、热重载或事件丢失后的初始同步。事件订阅不能是唯一数据来源。

### 4.4 状态机

合法状态转换：

```text
queued -> running
queued -> cancelled
running -> finalizing
running -> failed
running -> cancelled
finalizing -> succeeded
finalizing -> failed
finalizing -> cancelled（仅在底层仍可中止时允许）
```

终态任务不可再次被取消。重试应创建新的 `taskId`，保留 `retryOf` 关联，不能复用旧任务 ID，否则旧事件可能污染新任务。

### 4.5 取消实现

1. 每个任务创建独立 `context.WithCancel`。
2. 上传和下载底层循环改为可感知取消的 reader/writer 包装器，或在每次读写前检查 context。
3. 取消时停止调度队列中的任务，运行中的任务尽快退出。
4. 上传取消后删除临时远端文件，不得提交不完整的目标文件。
5. 下载取消后删除临时本地文件，不得替换已有目标文件。
6. 将 `context.Canceled` 映射为稳定的 `CANCELLED` 错误码，前端状态显示为 `cancelled`，不显示普通失败。
7. 取消操作幂等；重复点击不产生重复事件或错误弹窗。

注意：无法保证正在进行的单次网络系统调用立即中断，因此 UI 应先把按钮置为“正在取消”，最终以任务终态事件为准。

### 4.6 重试实现

重试仅允许失败或已取消任务。重试时：

- 复用已保存的源/目标参数，不依赖当前面板状态；
- 重新做本地路径、会话和远端路径校验；
- 创建新任务 ID；
- 继承原任务的方向、文件名、session 和目录；
- 将新任务置为 `queued`；
- 旧任务保留到自动清理或用户清除。

不默认自动重试网络失败，避免重复覆盖远端文件或让用户误以为任务仍在运行。

### 4.7 进度、速度和 ETA

后端事件至少携带：

```ts
interface TransferProgressEvent {
  taskId: string
  sessionId: string
  transferred: number
  total: number
  state: TransferState
  timestamp: number
  error?: string
}
```

速度和 ETA建议由前端根据事件时间窗口计算，原因是不同 UI 展示端可能需要不同的平滑策略。计算规则：

- 使用最近 1.5 至 3 秒的累计增量，不使用单次事件差值；
- 速度使用指数移动平均或加权移动平均；
- 传输量倒退时重置采样窗口，不能显示负速度；
- 速度低于有效阈值时显示“计算中”，不显示巨大 ETA；
- `total <= 0` 时百分比和 ETA 显示未知；
- ETA 采用 `ceil((total - transferred) / smoothedSpeed)`，小于 1 秒显示“即将完成”；
- 最终态不继续刷新速度，成功显示“已完成”，取消/失败显示状态文本。

后端事件节流可从固定 80ms 调整为 100 至 200ms，前端用 CSS 过渡或采样值平滑视觉，不用高频 React 重渲染制造跳动。

## 5. 前端实施计划

### 5.1 新增全局 TransferCenter

建议新增：

```text
src/renderer/src/components/TransferCenter.tsx
src/renderer/src/hooks/useTransferTasks.ts
```

在 `App.tsx` 顶层挂载，使其不依赖 `SftpPanel` 是否展开或当前活动 session。组件包括：

- 右上角入口按钮；
- 活跃任务数量徽标；
- 可展开/收起的浮动面板；
- 任务列表；
- 任务级操作按钮；
- 清除已完成按钮；
- 空状态。

入口按钮只使用熟悉的传输/队列图标，提供 tooltip、`aria-label` 和 `aria-expanded`。按钮不使用长文本占位，不遮挡窗口系统控制区。

### 5.2 任务项信息

每个文件任务显示：

- 文件名；
- 上传/下载方向图标和文字；
- 所属会话名称；
- 百分比；
- 已传大小 / 总大小；
- 平滑后的速度；
- 剩余时间；
- 状态：排队、传输中、整理中、已完成、失败、已取消；
- 任务级操作：取消、重试、清除。

文件名过长时单行省略并提供 title；大小、速度、时间采用固定宽度或 tabular numbers，避免数字变化导致布局抖动。

### 5.3 面板定位和尺寸

- 面板固定在主窗口内容区右上角，不覆盖设置模态框等高优先级模态层；
- 建议宽度 380 至 440px，最大高度为视口高度减去顶部安全间距；
- 任务列表垂直滚动，单任务卡片不能嵌套额外卡片；
- 面板展开/收起使用短时 opacity/transform 动画，并遵守 `prefers-reduced-motion`；
- 窄窗口时改为左右边距 12px、宽度 `min(420px, calc(100vw - 24px))`，不得横向溢出；
- 传输入口在有活跃任务时保持可见，完成任务自动消失不应让入口位置跳动。

### 5.4 自动消失策略

默认策略：

| 任务状态 | 保留时间 |
| --- | ---: |
| 成功 | 8 秒 |
| 已取消 | 12 秒 |
| 失败 | 30 秒 |

补充规则：

- 任务中心展开时暂停自动清理倒计时；
- 鼠标悬停或键盘焦点在任务项内时暂停倒计时；
- 仍有排队/运行任务时，已完成任务仍可短暂保留，但不超过上述时长；
- 失败任务自动消失后不影响重试入口的任务状态；应保留最近失败任务至少到 30 秒或直到用户清除；
- 用户执行重试后，旧任务和新任务短暂同时显示，避免用户误认为重试没有发生；
- 有活跃任务时不自动收起整个面板，只有任务项自动清理。

### 5.5 SftpPanel 改造

从 `SftpPanel` 移除单个 `transfer` 状态和标题栏中的单任务进度 badge。SFTP 面板保留文件列表、路径和拖放反馈，但上传/下载动作改为调用全局任务 API。

SFTP 面板只需要：

- 入队上传并固定当前 `sessionId` 与 `cwd`；
- 入队下载并固定当前远端文件路径和本地目标路径；
- 在任务成功后按任务会话刷新对应列表，不能只刷新当前活动 session；
- 不承担全局任务展示。

刷新列表时需要增加 session/目录校验，防止旧任务完成后刷新覆盖用户正在查看的新目录。

## 6. UI 操作定义

### 6.1 取消

- 排队任务：立即进入已取消；
- 运行任务：显示“正在取消”，待后端确认后进入已取消；
- 整理中任务：若已无法安全中止，按钮禁用并提示正在完成；
- 取消成功后不留下远端半文件或本地半文件。

### 6.2 重试

- 仅失败和已取消任务显示重试；
- 重试使用原任务参数，不继承已传字节，重新从 0 开始；
- 新任务排队时显示独立进度项；
- 原任务错误详情保留，便于比较重试结果。

### 6.3 清除

- 清除单个终态任务只从任务列表移除，不删除已成功文件；
- 清除已完成只处理成功、失败、取消，不影响排队和运行任务；
- 运行任务不允许被“清除”绕过取消流程。

## 7. 测试计划

### 7.1 后端任务管理器

必须覆盖：

1. 任务 ID 始终唯一；
2. 全局最多 3 个运行任务；
3. 同一 session 同时只有 1 个运行任务；
4. 不同 session 可以并行；
5. 队列按加入顺序调度，同时跳过被同 session 占用的任务并继续调度其他 session；
6. 排队任务取消后不会启动；
7. 运行任务取消会触发 context，并最终发出 cancelled；
8. 取消重复调用幂等；
9. 失败任务只发一次 failed 终态；
10. 字节达到 total 后仍经历 finalizing，只有提交成功才 succeeded；
11. 重试生成新 taskId 并继承固定参数；
12. 管理器销毁时取消所有运行任务并清理资源。

### 7.2 SFTP 服务

1. 上传取消清理远端临时文件，不提交目标文件；
2. 下载取消清理本地临时文件，不替换旧文件；
3. 上传/下载失败保留原子替换保证；
4. 当前目录在任务创建时固定，后续 `Chdir` 不影响任务目标；
5. 多文件批量任务各自发出独立事件；
6. 文件总大小为 0 时显示完成但不产生除零问题；
7. 传输事件字节数单调递增且不超过 total；
8. home boundary 和远端路径安全校验在重试时重新执行。

### 7.3 前端 hook/adapter

1. 初始任务快照正确建立；
2. 事件按 taskId 更新，不会因同名文件或同 session 覆盖；
3. 乱序/重复事件不会回退进度或重复终态；
4. 速度采用窗口平滑，不因单次大间隔显示异常值；
5. total 为 0 或未知时显示稳定占位；
6. 自动清理定时器在 hover、focus、面板展开时暂停；
7. 取消、重试、清除调用正确 API；
8. 事件订阅和组件卸载正确释放。

### 7.4 TransferCenter UI

1. 多个上传、下载任务分别显示；
2. 排队、运行、整理、成功、失败、取消状态视觉区分明确；
3. 长文件名、超大数字、中文/英文文案不撑破布局；
4. 入口徽标准确反映活跃任务数量；
5. 面板展开/收起不影响任务继续；
6. 取消按钮只操作对应 taskId；
7. 失败重试生成新任务项；
8. 成功任务按 8 秒自动消失，失败任务按 30 秒自动消失；
9. reduced-motion 下没有强制动画；
10. 键盘可聚焦、按钮有 aria-label，弹窗有合适的 dialog/region 语义。

### 7.5 SftpPanel 回归

1. 上传和下载动作仅入队一次；
2. 批量上传拆成多个任务；
3. 任务完成后只刷新对应 session 和目标目录；
4. 用户切换 session 或 SFTP 目录后，旧任务仍在全局中心显示；
5. 拖放上传与文件选择上传共用任务入口；
6. 不再显示会覆盖多个任务的旧单条 badge。

## 8. 手动验收场景

### P0：核心任务流

1. 在会话 A 选择 4 个文件上传，确认每个文件各有一条任务。
2. 观察最多 3 个全局运行任务，同一会话最多 1 个运行任务，其余排队。
3. 再在会话 B 发起下载，确认会话 B 任务可与会话 A 任务并行。
4. 切换会话、折叠 SFTP、切换远端目录，确认任务中心仍显示正确任务。
5. 任务完成后确认远端/本地文件正确，100% 后不会提前显示成功。

### P0：操作和异常

1. 取消排队任务，确认该任务不启动。
2. 取消运行中的大文件，确认最终状态为已取消且无残留临时文件。
3. 制造网络或权限失败，确认显示失败原因且可重试。
4. 重试失败任务，确认产生新任务 ID 和独立进度。
5. 连续点击取消、重试、清除，确认不会重复执行或崩溃。

### P1：展示质量

1. 验证文件名、方向、百分比、已传/总大小、速度、剩余时间全部可读。
2. 验证速度在小文件、慢网络和突发网络条件下不剧烈跳动。
3. 验证中文和英文下任务项不重叠、不横向溢出。
4. 验证 100%、125%、150% 系统缩放。
5. 验证窄窗口时右上角面板不遮挡主要操作且能完整收起。
6. 验证深色、浅色主题和 `prefers-reduced-motion`。

1. 定义共享任务类型、状态机和 IPC 事件契约。
2. 实现后端单任务上下文取消和 finalizing 状态。

## 10. 风险与边界

- 第一版不做暂停/继续，不设计断点状态字段，不复用部分已传文件作为续传依据。
- “同一 SSH 会话最多 1 个”是任务调度限制，不代表不同 SFTP 客户端不能被其他功能访问；需要确认现有 session/SFTP client 的并发安全性。
- 取消依赖底层网络读写可中断程度；最终状态必须由后端确认，不能由前端单方面改写。
- 下载任务需要在创建时确定保存路径；如果下载对话框必须由用户交互触发，应先打开对话框再创建任务，不能让后台任务等待一个未完成的对话框。
- 上传覆盖目标文件沿用现有原子替换策略；重试不会自动跳过同名目标，需在 UI 或产品规则中明确“覆盖”行为。
- 任务列表是内存态还是持久化历史需控制范围。第一版建议只保留应用运行期间的任务，不把本地路径和传输历史写入设置文件。
- 应用退出时应取消运行任务并等待有限时间清理临时文件，不能阻塞窗口无限关闭。

## 11. 验收门槛

完成以下条件才算第一版完成：

- 多文件任务按文件独立展示，taskId 更新准确，无覆盖；
- 全局并发不超过 3，同一 session 不超过 1；
- 任务与 SFTP 面板、当前会话和当前目录解耦；
- 取消可真正停止排队或运行任务，并清理临时文件；
- 重试生成新任务并使用原始固定目标；
- 显示文件名、方向、百分比、已传/总大小、速度、剩余时间；
- 速度和 ETA 在慢速、突发和小文件场景下稳定；
- 成功 8 秒、取消 12 秒、失败 30 秒自动清理，展开/悬停/焦点时暂停；
- 所有任务级操作只影响目标 taskId；
- 后端、adapter、hook、TransferCenter、SftpPanel 回归测试通过；
- `npm run typecheck`、`npm run lint`、`npm test`、`go test ./...` 和 `npm run build:wails` 通过；
- Windows 真实 Wails 构建完成核心上传、下载、取消、重试和多会话人工验收。

## 12. 本计划的非目标

- 不实现暂停/继续和断点续传；
- 不改变 SFTP 权限、路径安全和原子替换策略；
- 不把传输中心做成独立操作系统窗口；
- 不在第一版加入持久化传输历史；
- 不以总进度替代每文件进度；
- 不通过提高事件频率来掩盖任务模型缺失。
